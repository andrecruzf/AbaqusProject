\chapter{Numerical Model}\label{chap:numerical_model}

\section{Framework Overview and Contributions}

A simulation framework was developed in Abaqus/Explicit to build, run, and
post-process the Nakazima, Marciniak, and Punch-in-Punch configurations of
Task~I without manual intervention. The full model is generated from a single
configuration file: the framework creates the tooling, meshes or imports the
blank, assigns the Hosford--Coulomb material, applies contact and boundary
conditions, writes the input deck, submits the explicit job on Euler, and
extracts the forming-limit data from the resulting output database (ODB).
Campaign-specific numerical values are reported with the results in
Chapter~\ref{chap:results}, and the complete list of configuration controls is
collected in Appendix~\ref{app:configuration_parameters}.

The framework is built around four properties that the project requires:
\begin{itemize}
  \item \textbf{End-to-end automation.} The complete chain --- model build,
  solver submission, ODB post-processing, and FLC aggregation --- runs without
  manual Abaqus/CAE editing, so that complete campaigns and parameter studies
  can be launched from configuration alone.
  \item \textbf{Cross-configuration comparability.} A single pipeline and a
  fixed post-processing schema serve all three test types, so that differences
  in the extracted forming limits reflect the configuration rather than separate
  model definitions.
  \item \textbf{Controlled discretisation.} Element size is set by
  configuration-driven meshing rather than by manually edited models, which
  enables systematic mesh-refinement and mass-scaling studies at a consistent
  element size across specimen widths and configurations.
  \item \textbf{Physical fidelity.} A solid through-thickness discretisation
  with a Hosford--Coulomb VUMAT resolves fracture and element deletion, and
  three complementary limit criteria connect the numerical results to the
  identification framework of Chapter~\ref{chap:identification_framework}.
\end{itemize}

The remainder of this chapter describes the physical model, the numerical
controls, and the automated post-processing. Implementation-level details ---
output-request lists, the post-processing file catalogue, and the element and
keyword identifiers referenced below --- are collected in
Appendix~\ref{app:numerical_implementation}.

\section{Physical Model}

\subsection{Geometry and Symmetry}

To reduce computational cost, only one quarter of the specimen is simulated. The
blank lies in the global $X$--$Y$ plane and the forming direction is the global
$Z$ direction, with symmetry boundary conditions applied on the two cut planes.
The rigid tools are represented analytically where possible, while the
Punch-in-Punch secondary punch can alternatively be imported from a prepared
CAE file.

For the standard Nakazima and Marciniak tests the model consists of four parts:
the deformable specimen, the punch, the die, and the blank holder. The Nakazima
punch is a hemispherical analytical rigid surface; the Marciniak punch is a flat
analytical rigid surface with an edge fillet consistent with the ISO~12004-2
tooling recommendation. The Punch-in-Punch model contains five parts: an annular
outer punch (Punch~1) that pre-forms the specimen, and a selectable inner punch
(Punch~2) that continues the forming operation in the second step, so that
different variants can be tested without changing the rest of the model.

A shared family of specimen geometries is used for the standard Nakazima and
Marciniak configurations, which keeps the model topology and post-processing
sets consistent across campaigns. Specimens can be obtained from three sources:
the preferred route is the BM mesh builder, which generates the blank from
parameterised geometry and mesh settings, while existing \texttt{.cae} and
\texttt{.inp} files can also be imported. The import path preserves the named
node and element sets required by the model --- the symmetry sets, outer-edge
set, top and bottom contact surfaces, and the element set used for local history
output (Appendix~\ref{app:numerical_implementation}).

\subsection{Discretisation and Mesh Control}

The deformable blank is discretised with linear reduced-integration solid brick
elements (Appendix~\ref{app:numerical_implementation}). A solid formulation is
used so that through-thickness strain and element deletion can be evaluated
consistently with the Hosford--Coulomb VUMAT; the number of elements through the
sheet thickness is configurable, and element deletion is driven by the material
state variable.

A central requirement of the project is that mesh density can be controlled
systematically across specimen widths and test configurations. The framework
therefore treats meshing as a configuration-controlled step rather than a fixed
property of each imported geometry. Several seed modes are available for imported
geometries; the radial-zone strategy keeps a fine central region near the punch
apex and applies progressively coarser seeds toward the flange. The target sizes
and refinement factors are reported with the sensitivity studies rather than
being fixed in the model description.

For post-processing, a dome observation zone is defined from the undeformed
element centroids, with radius $R_\mathrm{dome}=0.15\,D_\mathrm{punch}$,
following the ISO~12004-2 requirement that the fracture relevant for an FLC point
occur within 15\,\% of the punch diameter. This zone is used to classify dome
fracture, select critical elements, and extract local strain histories.

\subsection{Material and Fracture Model}

The blank material is defined by a user material subroutine (VUMAT) that combines
an anisotropic Hill-type yield and flow formulation with mixed Swift--Voce
hardening. Fracture initiation is described by the Hosford--Coulomb criterion,
after which the VUMAT damage variables control the element-deletion state. The
size of the material card and the solution-dependent variable set are given in
Appendix~\ref{app:numerical_implementation}; several state variables are
initialised explicitly in the generated input deck to avoid zero-valued initial
damage or failure-strain variables at the first increment and to keep the
Abaqus~2023 explicit run robust.

The material orientation is assigned through a local Cartesian coordinate system.
The orientation angle in the configuration file rotates the rolling direction in
the specimen plane, so the same numerical setup serves both rolling- and
transverse-direction studies. This is important for comparing the model against
the experimental orientation study (Section~\ref{sec:orientation_influence})
before the punch-diameter and thickness trends are discussed.

\section{Loading, Boundary Conditions, and Contact}

For Nakazima and Marciniak simulations a single explicit forming step is used.
The punch displacement, speed, and amplitude are user controlled: the
displacement can follow a smooth-step amplitude or an approximately
constant-velocity profile with short end ramps. The constant-velocity option is
useful when time-dependent necking criteria are studied, because it avoids
artificial deceleration of the punch close to fracture.

The Punch-in-Punch model uses two explicit steps. In the first, Punch~1 and
Punch~2 advance together to generate the pre-forming state; in the second,
Punch~1 is held fixed at its end-of-step position while Punch~2 continues the
forming process and drives the specimen to failure. The step amplitudes and
travel values are campaign settings and are documented with the corresponding
results.

The die and blank-holder reference points are fixed, and the punch reference
point is constrained in all degrees of freedom except the forming displacement.
The two specimen symmetry planes carry symmetry boundary conditions, and the
outer blank edge is fixed by default, which represents the clamping action while
avoiding the computational cost of a full closing simulation. All tool--blank
interactions use explicit surface-to-surface contact with hard normal behaviour
and Coulomb friction; the punch--blank and clamping coefficients are controlled
independently, and separately for Punch~1, Punch~2, and the clamping tools in the
Punch-in-Punch model.

\section{Numerical Control and Quasi-Static Verification}

Although the forming process is quasi-static, it is solved with Abaqus/Explicit.
Variable mass scaling is therefore used to reduce the computational cost by
targeting a user-defined minimum stable time increment. Because mass scaling
introduces artificial inertia, every completed simulation is verified through the
ratio of kinetic to internal energy, $\mathrm{ALLKE}/\mathrm{ALLIE}$. The energy
histories are written for each specimen, and the final acceptance of a run is
based on this ratio together with the stability of the extracted forming-limit
point.

The same framework performs the mass-scaling and mesh-refinement sensitivity
studies. These are not separate models: they are generated by changing the
relevant configuration values while keeping the geometry, material model,
boundary conditions, output requests, and post-processing schema unchanged. This
makes the influence of the numerical settings traceable and allows the selected
production settings to be justified from runtime, quasi-static validity, and
strain-convergence metrics. The parameter grid is given in
Appendix~\ref{app:configuration_parameters} and discussed with the results.

\section{Automated Post-Processing and Limit Extraction}

After model generation, the input deck is augmented with a common set of field
and history output requests shared by all configurations
(Appendix~\ref{app:numerical_implementation}), so that every run produces
directly comparable data. Once the solver has finished, a single
post-processing script reads the ODB and writes a structured set of CSV files
(catalogued in Appendix~\ref{app:numerical_implementation}); the same script is
used for all test configurations.

The fracture endpoint is detected primarily from the punch force history: the
force maximum defines the last stable load point, while a configured post-peak
force drop is used to identify the crack frame. Element deletion provides the
fracture location and remains available as a fallback endpoint detector. If the
first deletion occurs outside the dome zone, the run is flagged as an
outside-dome or base fracture and is not treated as a valid FLC point.

When the required data are available, three complementary forming-limit rows are
written, mirroring the criteria of the identification framework:
\begin{enumerate}
  \item \textbf{Fracture limit.} The critical strain is taken at the last stable
  frame before fracture, at a critical element selected in the dome zone from the
  deletion or maximum-equivalent-plastic-strain information.
  \item \textbf{Volk--Hora necking limit.} A DIC-like region is built around the
  fracture neighbourhood; the mean thinning-rate history is fitted with a stable
  and an unstable branch, whose intersection defines the necking frame.
  \item \textbf{Damage-based limit.} The maximum dome-zone damage history is
  evaluated, and the inflection of this curve provides an additional
  damage-based necking indicator.
\end{enumerate}
This multi-criterion output is what links the numerical model to the Task~II
identification framework, allowing the same limit definitions to be compared on
experimental and numerical data. Diagnostic plots and movies are generated after
post-processing --- a per-run PDF with the strain path, force--displacement
curve, and quasi-static energy check, and a movie of the equivalent-plastic-strain
evolution and final fracture location --- and aggregation scripts combine the
per-width limits into FLC plots, so that the Nakazima, Marciniak, and
Punch-in-Punch configurations can be compared on the same strain-space axes.

\section{Execution on Euler and Parameter Studies}

The complete workflow is designed for the ETH Euler cluster. Models are built
with Abaqus/CAE in no-GUI mode, the input file and VUMAT are copied to scratch,
and the explicit solver is submitted with threaded CPU parallelisation. After the
ODB has been post-processed, the compact CSV files, figures, and movies are
copied back to the project directory while the large ODB remains in scratch
storage, which keeps the home directory small while retaining all data required
for analysis and plotting. Because parameter studies are generated by
configuration changes alone, the same execution path produces the factorial
mass-scaling and mesh-refinement grids discussed in Chapter~\ref{chap:results};
the pipeline architecture and cluster configuration are summarised in
Appendix~\ref{app:pipeline}.
