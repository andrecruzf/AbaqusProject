For the current scalar sensitivity study, mass scaling and mesh refinement are
not treated as a fully factorial grid. Instead, two independent sweeps are run
on the same Nakazima W100 reference case with a \SI{100}{\milli\meter} punch
and a fixed punch speed of \SI{5}{\milli\meter\per\second}. This keeps the
number of Abaqus token-consuming jobs manageable and separates inertial effects
from spatial-discretisation effects.

\section{Numerical Framework Implementation Details}
\label{app:numerical_implementation}

Chapter~\ref{chap:numerical_model} describes the framework at the level of
modelling choices and data flow. The implementation-level identifiers, the
enforced output requests, and the post-processing file catalogue referenced
there are collected here.

\subsection{Element and Model Identifiers}

\begin{tabbing}
 \hspace*{4.0cm} \= \kill
 \texttt{C3D8R}                \> 8-node linear brick element with reduced integration (deformable blank) \\[0.5ex]
 \texttt{XSYMM}, \texttt{YSYMM} \> Symmetry boundary conditions on the two quarter-model cut planes \\[0.5ex]
 \texttt{STATUS}              \> Element-deletion state used for fracture-location and fallback endpoint detection \\[0.5ex]
 \texttt{SDV6}                \> Damage solution-dependent variable used for the damage-based limit \\[0.5ex]
 \texttt{VUMAT\_explicit.f}   \> Hosford--Coulomb user material (46 material constants, 17 SDVs)
\end{tabbing}

Hourglass control is assigned through the solid-section controls, and element
deletion is enabled through the VUMAT state variable. Several solution-dependent
variables are initialised explicitly in the generated input deck to avoid
zero-valued initial damage at the first increment.

\subsection{Enforced Output Requests}

The input deck is modified after model generation to enforce a common output set
for all configurations:
\begin{itemize}
  \item \textbf{Field output:} stress, logarithmic strain, equivalent plastic
  strain, all solution-dependent variables, element status, triaxiality,
  Lode-related quantities, nodal displacement, and reaction force.
  \item \textbf{History output:} punch displacement and force, die and
  blank-holder reaction forces, whole-model energies (\texttt{ALLKE},
  \texttt{ALLIE}), and the history of a representative apex element.
\end{itemize}

\subsection{Post-Processing File Catalogue}

A single post-processing script reads the ODB and writes the following files,
which are identical in schema across all test configurations:
\begin{tabbing}
 \hspace*{4.0cm} \= \kill
 \texttt{punch\_fd.csv}       \> Punch force--displacement history \\[0.5ex]
 \texttt{energy\_data.csv}    \> Whole-model energy histories and the ALLKE/ALLIE ratio \\[0.5ex]
 \texttt{global.csv}          \> Per-frame global summary quantities \\[0.5ex]
 \texttt{strain\_path.csv}    \> Major/minor strain path of the critical dome element \\[0.5ex]
 \texttt{elout.csv}           \> Local history output of the apex element set \\[0.5ex]
 \texttt{forming\_limits.csv} \> Extracted fracture, Volk--Hora, and damage-based limit points
\end{tabbing}

\section{Running a Simulation Campaign}

Because Abaqus token availability limits the number of simultaneous solver
jobs, the current workflow submits scalar simulations sequentially. A single
case is launched from the local machine with \texttt{deploy.sh}; the script
pushes the current project files to Euler and starts \texttt{submit\_one.sh} in
a remote \texttt{tmux} session. The positional arguments are test type,
thickness, orientation, specimen width, PiP punch identifier, mesh-refinement
factor, and mass-scaling target:
\lstset{language=bash,numbers=none}
\begin{lstlisting}[frame=lines]
# One scalar W100 Nakazima run:
./deploy.sh nakazima 1.5 0 100 none 2 1e-5

# Mass-scaling sweep: repeat manually, one value at a time.
./deploy.sh nakazima 1.5 0 100 none 2 1e-6
./deploy.sh nakazima 1.5 0 100 none 2 5e-6
./deploy.sh nakazima 1.5 0 100 none 2 1e-5
./deploy.sh nakazima 1.5 0 100 none 2 5e-5
./deploy.sh nakazima 1.5 0 100 none 2 1e-4

# Mesh-refinement sweep: repeat manually, one value at a time.
./deploy.sh nakazima 1.5 0 100 none 1 1e-5
./deploy.sh nakazima 1.5 0 100 none 2 1e-5
./deploy.sh nakazima 1.5 0 100 none 3 1e-5
\end{lstlisting}

Results are written to scratch during the solver run and the compact output
files are copied back to the Euler home directory after post-processing. The
large ODB remains in scratch storage.

\section{Cluster Configuration}

Simulations run on the ETH Euler cluster (\texttt{acruzfaria@euler.ethz.ch}) using SLURM. Each solver job currently requests 24 CPUs, 4\,GB per CPU, and a 48-hour time limit. The Abaqus module is loaded via \texttt{module load abaqus/2023}. Post-processing scripts use \texttt{xvfb-run} for headless ODB rendering. Results are stored in \texttt{/cluster/scratch/acruzfaria/} during the run and copied to \texttt{/cluster/home/acruzfaria/} on completion.

\chapter{User Interface}
\label{app:interface}

The framework includes a graphical interface, built with Streamlit, that acts as
a front-end to the configuration file described in
Chapter~\ref{chap:numerical_model}. It is a finished, working tool that makes the
pipeline more convenient to use, and it can serve as a basis to inspire future
development.

Figure~\ref{fig:app_interface} shows the main view. The interface is organised
into four areas: \emph{Submit Job}, which exposes the case parameters (test type,
specimen width, sheet thickness, orientation, punch diameter, mesh factor and
thickness seeds, mass scaling, punch speed, punch travel, velocity profile, and
friction) together with the computational resources and the advanced mesh
settings; \emph{Job Status}, for monitoring submitted cluster jobs;
\emph{Results}, for inspecting the post-processed outputs; and an experimental
\emph{AI Assistant}. Each control writes the corresponding configuration value,
so a case prepared in the interface is equivalent to one configured directly in
the configuration file.
